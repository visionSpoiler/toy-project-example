# 기획·설계 문서 풀세트 작성 가이드 (생성형 AI 배포용) v1.0

> **이 문서의 용도**: 이 파일 하나를 생성형 AI(어떤 제품이든)에게 전달하면, AI가 **기획·설계 문서 13종 전체**를 규격에 맞게 작성할 수 있도록 만든 작업 지시서입니다.
> **자기완결**: 다른 문서를 읽지 않아도 작업이 가능하도록 필요한 규격·목차·판정 기준을 모두 이 안에 담았습니다.
> **버전**: v1.0 (2026-10-15) · **대상**: 소프트웨어 제품·서비스·플랫폼의 기획~설계 단계

---

## 0. 사용법 (사람이 읽는 부분)

1. 이 파일을 AI에게 **첨부하거나 전문을 붙여넣습니다**.
2. 아이디어·요구사항을 담은 입력 자료를 함께 줍니다(§7 틀 사용).
3. §6의 **단계별 프롬프트를 순서대로** 실행합니다. 한 번에 13종을 다 시키지 마십시오 - 앞 문서가 뒤 문서의 입력이 됩니다.
4. 각 단계가 끝나면 §5 완성도 기준으로 점검한 뒤 다음 단계로 넘어갑니다.

> **한 번에 다 시키면 안 되는 이유**: 기획이 흔들린 채로 화면·데이터·API를 만들면 전부 다시 써야 합니다. 앞 문서를 확정하고 다음으로 갑니다.

## 1. 용어 (이 문서 안에서 정의가 닫히도록)

| 용어 | 뜻 |
|------|-----|
| 문서 풀세트 | 아래 13종 전체 |
| FR / NFR | Functional Requirement(기능 요구) / Non-Functional Requirement(성능·보안·가용성 등 비기능 요구) |
| SLO | Service Level Objective - 응답시간·가용률 같은 목표 수치 |
| RTM | Requirements Traceability Matrix - 요구사항이 화면·데이터·API·테스트로 이어지는지 보여주는 추적표 |
| ERD | Entity Relationship Diagram - 데이터 구조도 |
| ADR | Architecture Decision Record - 중요한 기술 결정 1건을 배경·대안·결론·영향으로 적은 기록 |
| IA | Information Architecture - 메뉴·화면 구조 |
| 메타블록 | 문서 맨 위에 두는 작성 정보표(작성일·버전·작성방식·정합 기준) |
| as-built | 이미 만든 결과물을 역으로 문서화하는 방식 |
| 흡수 | 별도 파일을 만들지 않고 상위 문서의 고정 섹션으로 넣는 것 |
| 완성도 게이트 | 다음 단계로 넘어가도 되는지 판정하는 체크 기준 |

## 2. 산출물 13종과 작성 순서

| # | 문서 | 한 줄 역할 | 필수 |
|---|------|-----------|------|
| 00 | 문서 세트 정의서 | 이 규격 자체(본 가이드로 갈음 가능) | 선택 |
| 01 | INDEX + 추적표(RTM) | 문서 지도 + 요구사항 추적 | 필수 |
| 02 | 기획서 | 목적·대상·범위를 못박음 | 필수 |
| 03 | 기능명세서 | 무슨 기능을 어떻게(+NFR·SLO) | 필수 |
| 04 | 화면 설계서 | 화면 목록·배치·이동 | UI 있으면 필수 |
| 05 | UI 디자인시스템 / IA | 색·글꼴·간격·메뉴 구조·접근성 | UI 있으면 필수 |
| 06 | 데이터 모델 설계서(ERD) | 어떤 정보를 어떤 표에 | 필수 |
| 07 | API 명세서 | 화면과 데이터를 잇는 창구 | API 있으면 필수 |
| 08 | 시스템 아키텍처 + ADR | 전체 구조 + 중요 결정 기록 | 필수 |
| 09 | 보안·개인정보 설계서 | 인증·권한·개인정보 보호 | 필수 |
| 10 | 테스트·QA 전략서 | 무엇을 어떻게 검증 | 필수 |
| 11 | 운영·배포 계획서 | 어떻게 띄우고 운영 | 필수 |
| 12 | 관측·로깅·감사 설계서 | 잘 도는지 기록·감시 | 권장 |
| 13 | 용어집 | 용어·약어 정리 | 권장 |

**작성 순서**

```
02 기획서
  └→ 03 기능명세  →  04 화면설계  →  05 UI·IA
        └→ 06 데이터모델 → 07 API → 08 아키텍처+ADR
              └→ 09 보안 → 10 테스트 → 11 운영·배포 → 12 관측
                    └→ 01 INDEX+RTM → 13 용어집  (마지막에 전체를 묶음)
```

- **01과 13은 마지막**입니다. 앞 문서가 다 나와야 추적표와 용어집을 채울 수 있습니다.
- UI가 없는 서비스는 04·05를 면제하고, **면제 사유를 01 INDEX에 적습니다**.
- API를 제공하지 않으면 07을 면제하고 같은 방식으로 기록합니다.

## 3. 공통 작성 규칙 (13종 전부 적용)

### 3.1 파일

- 파일명: `NN_문서명_vX.Y.md` (예: `02_기획서_v1.0.md`)
- 저장 위치: `docs/design/` (프로젝트 루트 기준)
- 형식: Markdown

### 3.2 메타블록 (문서 맨 위, 의무)

| 항목 | 값 |
|------|-----|
| 문서 유형 | 기획 / 설계 / 운영 … |
| 버전 | v1.0 |
| 작성일 | YYYY-MM-DD |
| 작성 방식 | 신규 / as-built |
| 정합 기준 | 무엇을 근거로 썼는지(참조 자료·코드 기준일·테스트 결과 등) |

### 3.3 변경이력 (문서 맨 아래, 의무)

| 일자 | 버전 | 변경 내용 | 작성 |
|------|------|---------|------|

### 3.4 추적성

- 모든 기능에 **FR ID**를 붙입니다(`FR-01`, `FR-02` …). 비기능 요구는 `NFR-01` 형식.
- 화면·테이블·API·테스트는 **어느 FR에 속하는지** 표기합니다.
- 01 INDEX의 RTM에 그 연결을 모읍니다.

### 3.5 상태 기호

`완료` / `부분` / `미작성` / `진행` 넷으로 표기합니다(기호를 쓸 경우 문서 안에서 뜻을 먼저 정의).

### 3.6 중복 금지

- 같은 내용을 두 문서에 적지 않습니다. 한 곳에 적고 **다른 곳에서는 참조**합니다.
- 06·07·12는 규모가 작으면 03 또는 08의 **고정 섹션으로 흡수**해도 됩니다. 흡수했다면 01 INDEX에 "흡수됨 - 어디에"를 적습니다.
- 흡수 시 섹션 번호를 고정합니다 - **기능명세서 §5 = API, §6 = 데이터 모델**.

### 3.7 금지 사항 (AI에게 특히 중요)

- **지어내지 않습니다**. 모르는 수치·사례·인용을 만들지 않고 `미정` 또는 `확인 필요`로 둡니다.
- 근거 없는 성능 수치·시장 수치를 쓰지 않습니다. 쓰려면 **출처와 가정**을 함께 적습니다.
- 실제 개인정보·계정·키를 예시로 쓰지 않습니다. 예시는 명백한 더미 값으로 만듭니다.
- 구분자로 em dash(—)를 쓰지 않고 일반 하이픈(`-`)을 씁니다.
- 표의 수치는 우측 정렬합니다.

## 4. 문서별 필수 목차

| **10 테스트·QA** | 테스트 레벨·범위 / 시나리오·커버리지 목표 / 회귀·자동화 / 환경·데이터 / 합격 기준 |

| **12 관측·로깅·감사** | 지표(요청수·오류율·지연) / 구조화 로깅 / 추적 / **감사 로그(쓰기 전후)** / 보존·대시보드 |

## 5. 완성도 게이트 (다음 단계로 넘어가는 기준)

각 문서를 끝낼 때마다 확인합니다.

- [ ] 메타블록·변경이력이 있다
- [ ] 필수 섹션이 **비어 있지 않다**(제목만 있고 내용이 없는 섹션이 없다)
- [ ] 기능에 FR ID가 붙어 있고, 뒤 문서가 그 ID를 참조한다
- [ ] 추측으로 쓴 수치·사실이 없다(있으면 `미정`으로 표시됐다)
- [ ] 앞 문서와 모순되지 않는다(범위·용어·기능 개수)
- [ ] 면제한 문서·섹션은 **사유가 기록**돼 있다

전체(13종)를 끝낸 뒤에는 추가로 확인합니다.

- [ ] RTM에서 **화면·API·테스트로 이어지지 않는 기능**이 없다
- [ ] 용어집에 정의되지 않은 전문 용어가 본문에 없다
- [ ] 문서 간 중복 서술이 없다(한 곳 + 참조)

## 6. 작업 프롬프트 (순서대로 복사해서 사용)

> `[ ]` 안은 본인 상황으로 바꿉니다. 각 단계 뒤에는 §5 체크를 수행합니다.

### P0 - 준비

```
첨부한 "기획·설계 문서 풀세트 작성 가이드"를 작업 규격으로 삼아줘.
이 프로젝트의 설계 문서를 docs/design/ 에 만들 거야.
규격(파일명·메타블록·변경이력·추적 ID·금지사항)을 요약해서 확인시켜 줘.
```

### P1 - 기획서 (02)

```
첨부한 아이디어 자료를 근거로 02 기획서를 작성해줘.
가이드 §4의 02 필수 섹션을 모두 채우고, 모르는 항목은 "미정"으로 두고 지어내지 마.
핵심 기능은 FR-01 형식으로 번호를 붙여줘.
결과는 docs/design/02_기획서_v1.0.md 로 저장해줘.
```

### P2 - 기능명세서 (03)

```
02 기획서를 근거로 03 기능명세서를 작성해줘.
기능마다 입력·처리·출력·예외를 적고, FR ID를 기획서와 일치시켜줘.
NFR·SLO 섹션은 목표 수치를 임의로 만들지 말고, 정해지지 않았으면 "미정(결정 필요)"으로 표시해줘.
docs/design/03_기능명세서_v1.0.md 로 저장.
```

### P3 - 화면 설계·UI/IA (04·05)

```
03 기능명세서를 근거로 04 화면 설계서를 작성해줘. 화면마다 ID를 붙이고 어느 FR을 구현하는지 표로 매핑해줘.
이어서 05 UI 디자인시스템·IA를 작성해줘(디자인 토큰·컴포넌트·메뉴 구조·접근성 기준).
각각 docs/design/04_화면설계서_v1.0.md · docs/design/05_UI디자인시스템_IA_v1.0.md 로 저장.
UI가 없는 서비스면 두 문서를 만들지 말고 그 사실과 사유를 알려줘.
```

### P4 - 데이터 모델·API (06·07)

```
03·04를 근거로 06 데이터 모델 설계서를 작성해줘(ERD + 테이블 정의서 + 코드·열거값 + 키·인덱스 정책).
이어서 07 API 명세서를 작성해줘(엔드포인트·요청/응답·인증·에러코드·버저닝·호출 예시).
각 테이블·엔드포인트가 어느 FR에 속하는지 표기해줘.
docs/design/06_데이터모델설계서_v1.0.md · docs/design/07_API명세서_v1.0.md 로 저장.
```

### P5 - 아키텍처 + ADR (08)

```
지금까지 문서를 근거로 08 시스템 아키텍처 설계서를 작성해줘(컨텍스트·컴포넌트·배포 구조·기술 스택·외부 연동·품질 속성 대응).
그리고 이 프로젝트에서 이미 내려진 중요한 기술 결정 2~3개를 ADR로 기록해줘.
ADR 1건 형식: 제목 / 상태 / 맥락과 문제 / 검토한 대안 / 결정 / 결과(장점과 감수할 점).
docs/design/08_아키텍처_ADR_v1.0.md 로 저장.
```

### P6 - 보안·테스트·운영·관측 (09~12)

```
09 보안·개인정보 설계서를 작성해줘. 인증·인가, 데이터 보호, 위협 모델,
개인정보 처리(수집·동의·보존기간·파기·접근통제·로깅)를 포함하고,
개인정보를 다루지 않으면 그 사실을 명시해줘.
이어서 10 테스트·QA 전략서, 11 운영·배포 계획서, 12 관측·로깅·감사 설계서를 차례로 작성해줘.
각각 docs/design/09~12 파일로 저장.
```

### P7 - 묶기 (01·13)

```
docs/design/ 의 모든 문서를 근거로 01 INDEX + 추적표(RTM)를 작성해줘.
RTM은 FR ↔ 화면 ↔ 테이블 ↔ API ↔ 테스트가 한 줄로 이어지게 만들고,
연결이 끊긴 기능이 있으면 표 아래에 "미연결" 목록으로 따로 보여줘.
이어서 13 용어집을 만들어줘(본문에 쓰인 전문 용어·약어·상태값, 가나다순).
docs/design/01_INDEX_RTM_v1.0.md · docs/design/13_용어집_v1.0.md 로 저장.
```

### P8 - 최종 점검

```
첨부한 가이드 §5 완성도 게이트를 기준으로 docs/design/ 전체를 점검해줘.
1) 빠진 문서·빈 섹션
2) RTM에서 화면·API·테스트로 안 이어진 기능
3) 메타블록·변경이력 누락
4) 문서 간 모순(범위·기능 개수·용어)
5) 근거 없이 단정한 수치
빠진 것을 목록으로 먼저 보여주고, 내가 확인하면 채워줘.
```

### 재사용 프롬프트

```
R1 부분 수정   : [파일]의 [섹션]만 [이렇게] 바꿔줘. 나머지는 그대로 두고 바뀐 곳만 알려줘.

R3 규격 점검   : [파일]이 가이드 §3 공통 규칙과 §4 필수 목차를 지켰는지 점검해줘.
R4 역방향 정합 : [확정된 산출물]을 기준으로 상류 문서([04]·[05])를 되맞춰줘. 바뀐 항목을 표로 보여줘.
```

## 7. 입력 자료 틀 (아이디어 파일)

작성을 시작하기 전에 아래 틀을 채워 AI에게 함께 전달합니다. 비어 있는 칸은 AI가 되묻게 하면 됩니다.

```
# 프로젝트 입력
- 무엇: (무엇을 하는 제품인지 한두 문장)
- 누구를 위해: (주요 사용자)
- 왜: (어떤 문제를 해결하나)
- 핵심 기능: (3~7개, 줄마다 하나)
- 이번 범위 밖: (이번에 하지 않을 것)
- 제약: (기한·예산·기술·규제 중 정해진 것)
- 비슷한 서비스: (참고 대상이 있으면)
- 데이터: (다루는 정보. 개인정보 포함 여부)
- 운영 환경: (클라우드·온프레미스·사내망 등 정해졌으면)
```

> 비어 있으면 AI에게 **"부족한 부분을 한 번에 하나씩 물어봐 줘"**라고 요청해 문답으로 채웁니다.

## 8. 자주 생기는 실패와 대처

| 증상 | 원인 | 대처 |
|------|------|------|
| 문서가 그럴듯한데 숫자가 전부 가짜 | 근거 없이 생성 | §3.7을 다시 지시하고 "근거 없는 수치는 미정으로" 재작성 요청 |
| 뒤 문서가 앞 문서와 기능 개수가 다름 | 중간에 범위가 흔들림 | 02·03을 먼저 확정한 뒤 R4(역방향 정합)로 되맞춤 |
| 문서마다 같은 설명이 반복 | 중복 금지 미적용 | §3.6 적용, 한 곳만 남기고 나머지는 참조로 |
| RTM이 비어 있거나 형식만 있음 | FR ID 미부여 | 03으로 돌아가 FR ID부터 정리 |
| 용어가 문서마다 다름 | 용어집을 마지막에만 만듦 | 02 작성 시 핵심 용어를 먼저 고정하고 13에서 확장 |
